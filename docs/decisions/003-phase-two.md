# 003 — Accounts and vendor approval

2026-11-07. Phase 0/1 reverified before changes: lint/typecheck/build, 11 unit/API tests and 6 real MySQL tests passed. Preserve that foundation; stop after Phase 2.

- Use express-session with the maintained express-mysql-session store, existing durable schema, session regeneration at login, 30-minute idle and eight-hour absolute expiry. Every authenticated request compares ACTIVE status/auth_version from MySQL. Password change invalidates all sessions including the caller. No frontend authentication storage.
- Synchronizer CSRF token and exact configured Origin are both required for every mutation, including login/registration and multipart uploads. Development uses HTTP cookies; production requires HTTPS, Secure/HttpOnly/SameSite=Lax and __Host- prefix.
- Persistent, separately keyed account/IP throttles claim an attempt in a short database transaction before password hashing. Account: five attempts/15 minutes, IP: 30/15 minutes (avoids one typo locking a shared network). Successful login resets account failures only. Counters use HMAC identifiers and survive process restarts.
- Vendor profile versions: saving material changes or replacing documents opens a new DRAFT version and immediately hides the shop. Submitted snapshots/documents stay immutable. Explicit revise uses expected shop version. Suspension remains effective during revisions and can only be removed by admin review. Decisions require both shop version and submission version and operate under a shop lock.
- Configurable document types, default `business-proof` for local demonstration, not a statutory checklist. PDF/JPEG/PNG, at most 10 MB, signature detection, random private object keys, attachment downloads authorized on every request. Local storage is outside web assets; production uses an S3-compatible private bucket configuration. No service provisioned. Malware scanning and operator-approved retention/checklist remain prelaunch decisions.
- Bootstrap remains trusted CLI only. Admin user status changes are audited, revoke sessions and serialize last-active-admin protection with a database lock row. Vendor suspension/deactivation locks the shop first. No impersonation.
- Public directory returns only APPROVED shops with ACTIVE owners. Full catalogue/cart is Phase 3; ordering remains Phase 4.
- PR must also include uncommitted Phase 0/1 foundation because remote main contains only the specification. Use the GitHub connector to create a commit based on the actual remote parent if local Git authentication remains unavailable; never replace remote history.

Compatibility: express-session **1.19.0**, express-mysql-session **3.0.3**, Multer **2.5.0**, file-type **22.3.0** (Node >=22), AWS S3 SDK **3.1164.0** (Node >=20). All are pinned in the lockfile and compatible with the verified Node 24.22.2 runtime. Store table creation is disabled: versioned migrations own the schema. Production configuration rejects HTTP origins and local storage. Expired throttle buckets are pruned after 24 hours.

Official references checked: [session middleware](https://expressjs.com/en/resources/middleware/session/), [MySQL store configuration](https://github.com/chill117/express-mysql-session), [Multer limits](https://expressjs.com/en/resources/middleware/multer/). Installed package manifests were inspected for engine compatibility. The browser suite uses a dedicated disposable test server with HTTP test cookies, not a simulated claim that production TLS/S3 were verified.

PR #1 review correction (2026-11-07): the maintained store's default `set` upserts, so a request that loaded a session before logout could recreate its deleted row. The adapter now marks loaded/persisted server-side session data and uses UPDATE-only saves thereafter; only newly generated sessions use INSERT. InnoDB serializes DELETE and UPDATE on the session row, so neither ordering can leave a restored session after logout. Existing pre-fix records are marked when loaded. The maintained store still handles retrieval, expiry cleanup, touch and destruction. No migration, retained revocation tombstones or account-wide logout is needed. Registration forms are keyed by login/customer/vendor mode so route reuse cannot retain a prior role selection.
